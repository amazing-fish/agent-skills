# 深入审查，简短呈现

## 固定版本与范围

- 单个提交：比较该提交与选定父提交；merge commit 明确采用哪个父提交。
- PR/分支：通常 `git diff <base>...<head>` 展示从 merge-base 到 head 的提议改动；记录 merge-base，勿与 `git diff <base> <head>` 的两棵树比较混淆。
- 暂存区：使用 `git diff --cached`；工作区使用 `git diff`。整体未提交改动要分别保留 staged/unstaged，并记录未跟踪文件是否纳入。可将 diff 和纳入文件内容的摘要作为快照标识。
- 读代码与测试证据必须覆盖被检视输入；复用其他提交的运行结果须证明相关树、输入和环境仍适用，并保留原提交。仓库不干净时隔离验证或明确本地差异，不声称测到远端 HEAD。报告生成后 HEAD 改变则旧报告仍属于旧版本，不悄悄替换版本标签。
- 首屏给可辨识的短版本，证据区给完整版本。远端原始树无法获取或 patch 截断时如实记录缺口。

## 先验证发现，再决定怎么呈现

对每个候选发现确认：触发输入/状态是否真实可达、代码是否造成所述后果、调用方是否已处理、同一行为在 base 是否已存在、是否违反适用的需求或约束。

成立的发现应有“触发条件 → 改动位置 → 实际后果 → 处理建议”的短证据链。没有完整依据时，保留为待核实问题或残余风险；不要包装成确定缺陷。高影响但不确定的风险可影响结论，必须说明缺失哪项证据，不能用自评置信分数替代验证。

将严重性、证据确定性和来源分别表达。优先级可沿用仓库 P0–P3 口径；没有仓库口径时用“接受前修复 / 后续修复 / 提示”。遗留缺陷不得标为本次引入，但若新功能必然经过该缺陷路径，应提示对本次使用的影响。对同根因多处表现合并证据，不重复计数。

按实际需要检查失败、恢复、重试/幂等、并发/取消、权限、持久化、兼容与可观测性；不要向报告转录一张全维度检查表。架构漂移必须指向具体的职责越界、重复事实来源或契约改变，并说明行为或维护后果；不要用文件数量、行数或泛泛“耦合”判断腐化。

## 测试与产品判断

检查测试断言是否观察到要求的效果，mock 是否避开关键边界，fixture 是否只复制实现。对修复适用时检查用例能否在旧代码失败、新代码通过；不要为无行为变化的文案修改强行扩测。

证据至少区分：

| 来源 | 可作出的结论 |
| --- | --- |
| 本次执行、版本和环境明确 | 该命令/场景在记录环境下的实际结果 |
| 历史运行、CI 或作者提供 | 该来源报告的结果；注明版本、时间及可信限制 |
| 代码中存在测试，但未执行 | 有对应断言；本次运行结果未知 |
| 建议验证或尚缺材料 | 未验证；写明要解决的不确定性 |

不要将离线、模拟、实机、生产结果互相替代。没有独立产品判据时，不用实现输出反证实现正确。无法补足证据时，报告结论的范围和具体下一步。

## 复用证据与增量复核

先记录检视 base/head/merge-base、源树、相关依赖锁与构建配置、测试环境和证据时间，再判断复用范围。会话恢复不构成失效原因；版本号或提交 SHA 相近也不构成等价证明。

| 变化 | 可以保留 | 需要刷新或补验 |
| --- | --- | --- |
| 同一 HEAD，恢复会话 | 可追溯且仍适用的源码审查、测试和产物证据。 | 与下一动作有关的远端 PR、审核、检查、注册表或上游反馈。 |
| merge SHA 改变，文件树相同 | 已覆盖相同输入的源码与测试证据；注明测试原提交及等价依据。 | 合并事实、构建环境差异和实际制品身份；树相同不证明压缩包相同。 |
| base/HEAD/merge-base 改变 | 未受 delta 影响的可追溯证据。 | 重新计算实际 diff，检查新变化及其调用/依赖影响，生成当前版本报告并补受影响验证。 |
| 锁文件、构建参数、运行时或制品字节改变 | 未经过受影响边界的证据。 | 对应构建、安装、加载及行为检查；解释差异来源，必要时扩大验证。 |

报告应标明“本次执行”“沿用某版本结果，等价依据为……”或“尚未验证”。不能把历史 CI 成功写成当前提交刚刚跑过。合并授权由父工作流决定：证据可以复用，不代表旧批准自动适用于新 base/head。

增量复核不是只看新增几行：检查 delta 会影响的直接调用、契约和打包入口。没有充分依据缩小范围时，运行相关完整检查。必需检查、失败结果和未解决风险不能因复用而被跳过。

## 交互、性能与发布判断

交互修复先对应用户报告的动作和可见后果；实际组件截图、录制与自动化轨迹须说明数据来源、主题/视口、宿主及模拟边界。效果图证明观察到的表现，不能独立证明平均帧率、延迟改善或真实设备覆盖。

性能比较记录相同或可解释的工作负载、输入轨迹、运行时、设备和测量方法；选择能回答问题的帧工作耗时、布局/渲染次数或响应延迟。无基准或测量时，可以说明代码减少了某类工作，但不能宣称体验提升百分比或达到未经约定的阈值。

发布相关改动除源码外，还要按判断范围核对 source/tree、tarball digest/integrity、包清单、实际安装/入口加载和目标 registry/tag。不要虚构代码 diff 来描述纯发布状态；需要判断制品时记录真实快照和摘要。

- **代码可合入：** 当前 diff、行为和必要证据支持接受；不代表账号已授权或包已发布。
- **制品可发布：** 已核验的具体产物符合目标；实际上传仍受既有授权及服务认证约束。
- **发布已完成：** 目标版本/元数据和预期 tag 可查，下载制品与核验产物匹配，相关安装/加载检查通过。上传受理或命令退出 0 不足以单独得出此结论。
- **收录已完成：** 有上游接受或公开列表的对应证据。收录 PR 检查通过只能说明申请检查状态。

只呈现当前任务所需的判断及剩余阶段，不把这些分类变成报告必选章节。发现 registry 产物与核验摘要不一致时，停止“可发布/已完成”结论并明确缺口；不要为修正历史记录擅自改包或执行撤包。

## 链接与特殊文件

先读取 remote，确认平台和网页规则。GitHub 使用 `compare/<base_sha>...<head_sha>` 和 `blob/<sha>/<path>#Lx-Ly`；只用真实 SHA 与实际版本行号。按 URL 规则编码路径，勿根据仓库名猜测 remote。私有源码保持原访问边界。

对 rename、binary、generated/vendor、lockfile、submodule、LFS 和缺失 patch 分别记录实际检查方式。生成文件的元数据检查不等于逻辑审查；LFS 指针不等于读取对象；依赖锁变化不等于审核所有依赖。足以支撑判断的范围才称为已检视。

脚本的规模档位只用于安排证据：small ≤20 文件/800 改动行/128 KiB；standard ≤80 文件/4,000 行/1 MiB；需全部满足，超限为 large。无论规模，主报告仍围绕判断；不能用缩短正文为理由省略审查或掩盖关键风险。
