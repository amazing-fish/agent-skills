# PR 审查与判断

## 先核实，再判断

1. **PR 模式默认只接受已提交的 PR。** 从实际仓库读取 PR 目标、Issue/验收条件、`base_sha`、`head_sha`、变更文件、相关调用链、测试和 CI/Review 状态。固定版本；结束前重查 HEAD，漂移则重新核对相关结论。不要把 staged、working-tree、untracked 状态冒充已提交证据。若用户另有目标，应明确范围和证据限制，不套用 PR 合入结论。
2. **逐项对照需求和行为。** 追踪必要的跨文件输入、输出、状态、异常和回退路径，优先找可能改变用户体验或造成回归的行为；不能仅凭提交说明、测试名称或 Agent 自述断定功能已完成。
3. **区分事实与未知。** 将已确认的本次引入缺陷、主干既有问题、设计取舍、尚未验证的风险分别标注；缺少访问权限、测试结果、patch 或证据时直接披露。不要编造缺陷，也不要将“未验证”写成“已通过”。
4. **只做审查。** 不修改业务代码、不审批或合并 PR；报告里的“建议合入”不构成用户授权。

## 先给决策，再解释证据

生成的报告默认是**一屏可读的决策摘要**。正文按信息价值组织，不按文件顺序罗列；小改动应更短。

- **结论：** `建议合入` / `需要修改` / `证据不足，暂缓决定`，附一句具体原因。已确认的阻断缺陷应建议修改；关键验收或验证缺失应暂缓，不得靠主观信心放行。
- **解决什么：** 原问题、目标及真正交付的行为变化；无法确认的需求明确指出。
- **为什么这样做：** 核心机制、必要的跨组件关系及有意义的取舍。只有替代方案实质影响决策时才解释。
- **验证和风险：** 区分本次实际执行、仅由 CI/PR 提供、未执行的验证；突出兼容性、安全性、回归与残余未知。
- **下一步：** 需要修改的点，或需要谁确认哪一个问题。无问题时直接给出合入建议，不制造待办。

短摘要之后，只为**可执行发现、关键行为链、必要的验证证据**提供按需展开的细节。每个发现必须有严重度、触发条件、影响、可核对的文件/行证据和建议动作。无发现时明确写“未发现明确的本次引入缺陷”，不得推断为“绝无风险”。不要默认加入目录、文件清单式流水账、完整影响矩阵、通用替代方案、理解问答或冗长检查清单。

## 证据链接与保密

- GitHub PR 的所有规模**一律不在 HTML 中复制 raw diff、patch 或 diff hunk**；只放经过核对、固定到 `base_sha...head_sha` 的 compare 链接，以及固定到 `head_sha` 的文件/行永久链接。可用 PR 页面作导航，但不能替代固定版本证据。
- 不复制仓库源码、密钥、令牌、私有接口、身份信息或大量日志到报告；HTML 转义所有来自代码、Issue、评论和测试的外部文本。固定链接保留原仓库访问控制。
- 对二进制、生成文件、重命名、缺失 patch 或未审查区域，明确标注覆盖边界；不声称已检查无法读取的内容。只为可访问且经核实的仓库地址生成链接。


## 可选独立审查

仅在用户要求或高风险确有价值、且环境支持子 Agent 时启用。主 Agent 固定 base/head 和实际审查范围，子 Agent **只读**、**不修改产品代码**，**不要提供主 Agent 的预期结论**；结果按 `references/independent-review-contract.md` 与 `scripts/validate_independent_review.py` 校验，逐项复核后才采用。能力不可用、输出无效、超时或失败时**单 Agent 回退**；简要披露是否采用、覆盖范围、未检查部分与不确定性，不因此增加默认报告篇幅。
