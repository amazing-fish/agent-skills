# 流程、责任、要求与现状的图式

沿用 SKILL.md 的取证、保密与交付边界；本文件扩展呈现方式，不覆盖 PR 的审查或授权规则。按主问题选择需要的图式，不要求每份报告都展开整个系统。

## 先把关系讲对

1. 写出读者要理解的一个问题、一句有证据支持的回答、一个具体触发场景。先整理事实，再设计图。
2. 分开列出参与方、各自输入/输出、谁能修改哪一段。区分用户仓库、承载发布物的平台、第三方上游和本地客户端；“数据从这里经过”不等于“这里决定更新时机”。按实际系统取舍，不强凑四方。
3. 把接口条件／规范要求、项目自己的配置选择、上游当前实现分开标注。注释、实现和 README 不是自动成立的外部强制规范。
4. 对不同数据路径分别追踪来源、触发时机、版本、缓存与回退。绘制分叉路径，而不是把所有成功状态连成一条已经完成的流程。
5. 同时保留整体数据更新时间和单条记录采集时间；分开发布、采集、分发、本地读取。统一展示时区，区分计划触发、实际启动与完成时间。等待超过某个缓存时长，不证明上游已产生新数据。
6. 将观察、由代码推断的结果、待核实和模拟状态明确区分。公开源可以解释一种输出，不等于已在用户客户端复现；现场未读取的版本、安装来源和接口响应仍未知。历史快照注明取证时间，不冒充实时状态。

## 用一个主图组织报告

首屏用结果标题、短回答、取证版本/时间和关键限制。随后依问题选用下列模块，删除无用模块，不要求每份报告都具有目录、三种交互或固定章节数。

| 读者困惑 | 首选视觉 | 图必须回答 |
| --- | --- | --- |
| 哪些步骤或数据走不同路线 | 分支流程图、双路径图 | 每条箭头送什么，在哪分叉和回退 |
| 哪些属于我，哪些属于上游 | 按参与方排列的责任泳道 | 谁提供、谁承载、谁采集、谁展示，谁能改 |
| 为什么过了很久还没变化 | 同时区时间线 | 发布与采集的先后，计划与完成的区别 |
| 改一个条件会发生什么 | 少量状态切换 | 哪个输入改变了哪条分支与最终结果 |
| 下一步应该改哪里 | 小型责任表或并列行动区 | 动作、掌握控制权的一方、预期影响 |

- 主图应能独立表达核心机制；不要用纯文字卡片加箭头冒充流程图。给箭头标注数据或事件，给判断节点标注实际比较条件；用线型/文字补充颜色含义。
- 保持参与方颜色映射一致；状态成功/待处理/失败使用独立的语义标签，别把某个参与方永久画成失败方。各方颜色只服务辨认，不暗示控制权限。
- 桌面主图最多约五个横向节点；再多则分组、转为纵向或拆图。SVG 用 title/desc 和可读标签，不以装饰性指标代替解释。
- 采用宽约 1100–1240px 的主内容区，正文至少 16px。职责、时序、场景控制都靠近主图；证据、完整 SHA 和长命令放原生 `<details>`。核心结论与实质限制保持可见。
- 从 `assets/report-theme.css` 内联主题，再内联 `assets/report-layout.css`。图解根节点使用 `class="human-report"`；布局类只在此节点下生效。主题切换、打印、窄屏和键盘操作仍需可用。不要让图解宽布局覆盖紧凑改动汇报。

## 只加入能解释因果的交互

交互可选。它应改变输入、箭头/判断或结果，帮助读者比较真实分支，不能只换标题颜色。

- 区分“本次观察”“假设已同步”“假设已安装”等状态。观察中未知的值不能因为按钮切换而变成事实。用该任务的实际状态命名，不复用某次项目的版本号。
- 同时更新主图、选中控件和结论，使用原生按钮、`aria-pressed` 或完整 tab 语义；动态结果用 `aria-live="polite"`，支持键盘和触屏。
- 通过 `textContent` 或正确转义插入文本；不把外部数据写进 `innerHTML`。状态切换只在本页运行，不请求网络、不改配置、不执行真实操作。
- 不要把界面模拟称作现场截图、把规则演示称作端到端验证；若当前界面未必提供某入口，说明演示的是接口规则。
- 无脚本时，保留可读的默认主图和结论；打印时展示各状态的简短静态摘要，并展开必要证据。不要只在点击后才给出关键限制。

## 内容骨架示例

结构可调；下面是布局语义，不是每次都要填满的模板。

```html
<main class="human-report">
  <header class="rf-hero"><h1>有证据支持的结果</h1><p>问题、短回答与关键限制</p></header>
  <section class="rf-panel" aria-labelledby="flow-title">
    <h2 id="flow-title">核心关系</h2>
    <div class="rf-controls" role="group" aria-label="场景"><!-- 可选状态按钮 --></div>
    <div class="rf-flow"><svg role="img" aria-labelledby="diagram-title diagram-desc"><!-- 实际主图 --></svg></div>
    <p aria-live="polite"><!-- 当前分支结论 --></p>
  </section>
  <section class="rf-actions"><!-- 按需说明各方职责 --></section>
  <ol class="rf-stages"><!-- 按需说明历史与计划 --></ol>
  <details><summary>证据与适用边界</summary><!-- 固定版本、来源与验证范围 --></details>
</main>
```

## 完成前检查

- 读者只看主图，能否说出谁控制哪一段、什么条件改变结果、当前卡在哪里？图与正文是否使用同一组事实？
- 实际检查桌面与 390px 左右窄屏；窄屏优先纵向重排。不可避免的复杂关系才放有名称的横向滚动区域，不允许整页溢出；图中文字保持可读。
- 有交互时逐个执行状态、键盘操作、折叠证据与复位；检查无脚本首屏、明暗主题和打印摘要。只通过语法/静态检查时，不宣称视觉检查完成。
- 来源和测试能支持的结论有多大，就写多大。模板、示例与模拟数据不能被顺手带入下一份真实报告。
